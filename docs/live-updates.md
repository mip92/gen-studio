# Живые обновления UI: websocket очереди

**Правило одной строкой: во фронте не бывает `setInterval`. Свежесть даёт сокет, пробуждение вкладки и кнопка ⟳ — в этом порядке.**

До 2026-08-20 фронт держал ~26 независимых таймеров на 3–5 секунд. Страница
предметов с 12 предметами давала ~24 000 запросов в час **при пустой очереди**,
и ни один таймер не засыпал на скрытой вкладке. Основное рабочее устройство —
планшет по локальной сети, поэтому метрика тут не запросы, а **пробуждения
радиомодуля**: таймеры не давали ему заснуть никогда.

---

## 1. Как это устроено

```
ComfyUI / kohya / fish        (бэк узнаёт опросом — это НЕ изменилось)
        ↓
QueueLedgerService            все переходы статуса проходят здесь
        ↓ .broadcast()
QueueEventsService            in-process шина, счётчик seq
        ↓
ws://<host>:4000/ws/queue     широковещательно, входящие кадры игнорируются
        ↓
LiveEventsProvider            ОДИН сокет на вкладку (app/layout.tsx)
        ↓ useLiveEvents(match, onEvent, { active })
страница                      вызывает СВОЙ обычный REST-эндпоинт
```

**Событие не несёт данных.** Только факт, что что-то сдвинулось, плюс id для
фильтрации:

```ts
{ seq, at, op, scope, entryId, jobType, jobId, status,
  projectId, shotId, profileId, segmentId }
```

`op` — один из `enqueued` `claimed` `released` `closed` `moved` `reordered`
`prioritized`. `closed` — главный: он значит «работа закончилась».

Почему тонкое, а не с данными: страница шота хочет `renderedImages` и
`imageQcVerdicts`, страница очереди — сшитый `QueueRowDto` с позицией, статистика
проекта — прогноз. Ни одного из этих view-model нет в `queue_entries`. Положи в
событие строку очереди — и рефетч всё равно понадобится, зато формат провода
начнёт расходиться со схемой. Поэтому событие говорит только «перечитай», а что
именно перечитывать, знает страница.

---

## 2. Как подписать страницу

```tsx
const match = useCallback(on.all(on.shot(shotId), on.types('video', 'video_post')), [shotId]);
useLiveEvents(match, refresh, { active: anyInFlight });
```

- `match` — какие события твои. Матчеры в `lib/liveEvents.tsx`: `on.any`,
  `on.finished`, `on.project(id)`, `on.shot(id)`, `on.profile(id)`, `on.job(id)`,
  `on.types(...)`, и `on.all(...)` чтобы совместить.
- `onEvent` — **уже существующая** `refresh()` компонента. Не пиши новую.
- `active` — **держать ли соединение открытым**. Не фильтр уведомлений.

### `active` — ровно два значения

| значение | когда | примеры |
|---|---|---|
| `true` | страница существует, чтобы смотреть за работой, либо её собственный джоб в полёте | `/queue`, овервью, список актов, музыка, `active: anyInFlight` в панелях шота |
| `false` | джобовое состояние страница показывает попутно и обычно простаивает | статистика проекта, шелл персонажа, список предметов |

**`active: false` НЕ значит «не уведомлять меня».** Уведомления приходят всегда:
и когда сокет поднят кем-то другим, и при каждом пробуждении вкладки. Иначе
планшет, который взяли со стола, показал бы состояние до того, как его положили.

### Что перезапрашивать, а что нет

| эндпоинт | фильтр | почему |
|---|---|---|
| `/pipeline/queue` | фильтр по видимым типам и статусам (§2a) | сам эндпоинт дешёвый (3–6 индексированных запросов), но очередь глубокая — бланкетный `on.any` дёргает вью на событиях, которые его не меняют |
| `/projects/:id/stats` | `on.finished` + `on.project` | **тяжёлый**: прогноз, стоимость стадий, разбор потерь. Меняется только когда работа ЗАВЕРШИЛАСЬ. На `moved`/`prioritized` пересчитывать нечего |
| `/shots/:id` | `on.shot(id)` | средний, но нужен весь: рендеры и вердикты QC лежат там же |
| `/actions` | **никогда** | самый дорогой в системе: N+1 по профилям плюс синхронные `existsSync` на каждый профиль и каждого участника каждого шота, без `?project=` — по всем проектам. Он и так не поллится. Переводить его на push — значит перенести ту же работу с «каждый тик» на «каждую мутацию», то есть сделать хуже. Сначала лечить N+1 |
| списки TTS по шотам | `on.project` + `on.types('tts')` | фан-аут один запрос на видимый шот. Батч-эндпоинта нет, поэтому пачка на завершённую строку — приемлемо, а 33 запроса в секунду были нет |

## 2a. Фильтруй событие по тому, что вид РЕАЛЬНО показывает

`on.any` — почти всегда ошибка. Очередь глубокая (~1400 pending), слот один,
поэтому `closed` и следующий `claimed` летят парами непрерывно. Бланкетная
подписка перечитывала таблицу каждые пару секунд — в том числе на
`/queue/done?type=end_frame`, где захват video-джоба не меняет ни одной видимой
строки.

Два правила, по которым `QueueTable` строит фильтр из живого состояния фильтров:

- **Тип.** Если во вью включён фильтр по `jobType`, событие другого типа
  пропускай — оно не может ни добавить, ни убрать строку.
- **Терминальные статусы.** Вью, показывающий ТОЛЬКО терминальные статусы
  (`/queue/done`), меняется исключительно на `op === 'closed'`. Строк
  `enqueued`/`claimed`/`released`/`moved` в нём не было и не появится.
  **Обратный приём НЕ безопасен:** во вью с pending/running `closed`
  обязан вызывать рефетч — именно чтобы строка оттуда ушла.

Всегда пропускай насквозь: `e.seq === -1` (ресинк после реконнекта или
пробуждения) и `e.scope === 'bulk'` (`reordered`/`prioritized` меняют порядок
целиком). Образец — `queueMatch` в `QueueTable.tsx`.

## 2b. Всплески склеиваются, а UI обязан быть width-stable

У каждого подписчика на рефетче стоит трейлинг-дебаунс **250 мс** (`BURST_MS` в
`lib/liveEvents.tsx`): один диспатч рождает пару событий, перечитывать дважды
незачем. Это НЕ поллинг — без событий таймера не существует.

И отдельное правило вёрстки, купленное кровью: **ничто, чья ширина зависит от
живого состояния, не должно менять ширину.** У `RefreshControl` кнопка сначала
переключала подпись «⟳ Обновить» → «…», и на активной очереди она дёргалась
несколько раз в минуту. Подпись теперь постоянна, крутится только глиф, время —
`tabular-nums`.

## 3. Чего сокет не знает

Очередь фиксирует **начало и конец** джоба. Прогресса внутри джоба в системе
нет физически. Отсюда два известных компромисса:

- **`TrainingProgress`** (`components/CharacterDetail.tsx`) — счётчик шагов kohya
  («шаг 420/2000») больше не растёт на экране. Обновляется на старте, финише,
  пробуждении вкладки и по ⟳.
- **`TrainingHistoryChart`** — кривая лосса не дорисовывается по ходу обучения.

Чтобы вернуть живые счётчики, нужен **второй источник push** (tail лога kohya и
websocket ComfyUI, у которого есть `progress` с номерами шагов — сейчас
`comfy.service.ts` умеет только REST `/history`, то есть бинарное done/not-done).
Это отдельная задача, сознательно не сделанная.

## 4. Что на этой шине НЕ живёт

- **`PublishStepper`** — два его таймера следят за манифестом комикс-экспорта на
  диске, а не за `queue_entries`. Другая подсистема; таймеры оставлены осознанно.
- **`api.comfyQueue()`** в `ScenesList` — родная очередь ComfyUI (свои
  prompt-id), не наш журнал.
- **`prop_anchor` по предмету.** У `queue_entries` **нет колонки `propId`**,
  поэтому событие предмета фильтруется только до проекта. Все панели предметов на
  странице перечитывают, когда завершается любой предмет. Это один рефетч на
  завершённый рендер, а не на тик — терпимо. Настоящее лечение — миграция с новой
  колонкой.

## Грабли, на которые уже наступили

**Значение контекста обязано быть стабильным.** `status` лежал в том же
`useMemo`, что и `register` — на каждом переходе `idle→connecting→open` менялась
идентичность контекста, у всех подписчиков перезапускался эффект, половина
«unregister» на миг оставляла ноль активных подписчиков, сокет закрывался и
открывался заново. **Браузер открывал новое соединение каждую секунду.** Причём
на каждом `open` летит `fanOut(RESYNC)`, то есть шторм ещё и дёргал рефетч всего.
Теперь два контекста: `ApiCtx` (стабильный) и `StatusCtx` (волатильный).
**Никогда не сливать их обратно.**

**Register/unregister склеены отложенным `sync`.** React размонтирует старого
подписчика раньше, чем монтирует нового при смене `active`, поэтому немедленный
`sync` увидел бы между ними ноль подписчиков и снёс бы соединение впустую.

**Оптимистичное локальное состояние обязано уметь сойтись с сервером.** Флаг
`state.status='queued'` в `RenderSection` раньше сбрасывал поллер за 3 с, а на
сокете его снимало только событие по точному `jobId` — потерянное событие или
висящий POST оставляли «⏳ в очереди» навсегда. Теперь есть самопочинка от
`shot.pendingRenders` плюс guard на время запроса. При поллинге эта обязанность
была неявной: таймер прощал всё.

## 5. Эксплуатация

- **Порт.** Браузер идёт на `:4000` напрямую, НЕ через `/api`. `rewrites()` в
  Next не проксирует websocket-upgrade — по той же причине длинный
  комикс-экспорт уже ходит мимо прокси (`DIRECT_API_BASE` в `lib/api.ts`).
- **Пинг 30 с** только для обнаружения полумёртвых сокетов (роуминг Wi-Fi рвёт
  TCP без `close`). Вкладка в фоне сама закрывает соединение, так что по спящему
  планшету пинг не стреляет.
- **Один процесс — Redis не нужен.** Шина in-process. Если когда-нибудь появится
  второй воркер, широковещание сломается и понадобится pub/sub.
- **`seq` сбрасывается при рестарте бэка.** Клиент всё равно делает рефетч на
  каждом подключении, так что это диагностика, а не механизм.
- **Сокет не поднялся — не авария.** После 6 неудач подряд клиент перестаёт
  пытаться, и страница ведёт себя как `/actions`: пробуждение плюс кнопка.
  Ветки `if (sse) … else …` нет ни у одного компонента, и появляться не должно.

## 6. Добавляешь новый тип джоба

1. Статус пиши **только** через `QueueLedgerService` — тогда broadcast бесплатен.
   Своя запись в `queue_entries` мимо журнала = событие не улетит (тот же класс
   бага, что «невидимый pending», который не диспатчился).
2. Добавь тип в `JobType` (бэк) **и** в `QueueJobType` в `lib/liveEvents.tsx` —
   они дублируются руками, общего пакета нет.
3. Подпиши страницу через `useLiveEvents`. **Не** заводи таймер.
4. Нужен id, которого в `queue_entries` нет (как `propId`)? Либо фильтруй грубее
   по проекту, либо добавь колонку миграцией. Не проси событие носить данные.
